
# 📝 Engineering Notes: MT7628KN Hardware Bringup

## 🛠️ Hardware Profile

* **Device:** Generic Wall-Plug Wi-Fi Repeater ($5.00/each).
* **SoC:** MediaTek **MT7628KN** (MIPS32 24KEc core @ **575 MHz**).
* **System RAM:** **8 MB DDR1** (Integrated inside the CPU package; non-upgradeable).
* **SPI Flash:** Macronix **MX-12G** (**4 MB** non-volatile storage).
* **Green Loop Pinout (3-Pin Debug Header):**
* **Pin 1:** `GND` (True Digital Ground, 0V).
* **Pin 2:** `TX` (Serial Transmit, sits at **$3.24\text{V}$** idle / Active High).
* **Pin 3:** `RX` (Serial Receive, sits at **$0\text{V}$** waiting for input).



---

## 💾 Software Profile

* **Bootloader:** **Ralink U-Boot Version 4.3.0.0** (Built on U-Boot 1.1.3, dated Dec 13, 2017).
* **Serial Configuration:** `57600 baud`, 8N1 logic levels.
* **Console Access:** Unlocked. Sending character `4` aborts autoboot and opens the `MT7628 #` command line prompt.
* **U-Boot Network Environment:**
* `ipaddr = 192.168.11.8` (Repeater static IP)
* `serverip = 192.168.11.11` (Expected TFTP host machine IP)

* **Stock OS:** Compressed **830.7 KB** legacy Linux firmware image named **`zxrouter`** running a minimal BusyBox environment.

The web administration interface executes structural hardware modifications (like reboots, factory resets, or configuration upgrades) by sending raw HTTP requests targeting a specific virtual page wrapper called do_cmd.htm. It passes commands via hidden form variables like CMD and CCMD (which looks like a direct Command ID mapping, where 100 might equal system configuration actions).

In a poorly constructed eCos environment, these request endpoints frequently lack session token validation (CSRF protection).

If a browser passes a query parameter directly like http://192.168.11.8/do_cmd.htm?CMD=SYS_CONF&CCMD=100, the eCos binary parses the CMD string sequentially. If the parser inside the C file doesn't strictly check the privilege scope of the incoming connection before calling the system execution loop, anyone on the network can trigger actions without authenticating.

### 🍪 The "Cookie" Breakdown

When a user logs into this router, it doesn't use a secure, server-generated session token. Instead, the browser does this:

1. It takes the username (`admin`) and the password you typed (e.g., `88888888`).
2. It mashes them together: `admin:88888888`.
3. It runs them through **Base64 encoding** (which looks like `YWRtaW46ODg4ODg4ODg=`).
4. It saves that string directly into your browser's local cookies under the name `Authorization`.

**Why this is terrible:** Base64 is *encoding*, not *encryption*. Anyone who gets their hands on that cookie can just type `echo "YWRtaW46ODg4ODg4ODg=" | base64 -d` in their Linux terminal and instantly see the plaintext password.

---

### 💥 The Kill Chain: Combining XSS with the Cookie

This is where your hacking journey comes full circle.

Remember the XSS payload you just got to work? (`';alert('hacked')//`). You used it to pop up a harmless alert box. But because the Urant developers store the password in that unsecured cookie, an attacker wouldn't use `alert()`.

They would use your XSS injection point to write a payload like this:

```javascript

```

If the router admin clicks that poisoned link, the router will execute the XSS, grab the `Authorization` cookie right out of the browser's memory, and silently text message it to the hacker's server. The hacker decodes the Base64, gets the admin password, and owns the router.

*(Note: Modern web security uses a flag called `HttpOnly` to specifically block JavaScript from reading cookies to prevent this exact attack. Naturally, this router doesn't use it).*

### 🗺️ Browser Storage vs. Hardware Storage

* **The Browser (Cookies):** Stores the Base64-encoded password so the user doesn't have to log in every time they click a new menu tab.
